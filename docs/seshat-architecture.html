LEVEL ONE · WIDEST

Who uses it, and what it depends on

Three kinds of caller, one system, and exactly two things outside it: a folder on the host and Google's API. Nothing else is reached over the network at run time.

The library folder is the whole corpus, and it is a data source rather than a part of the system: put a text file in it and the file is the document. The gateway does write to it, in one direction and for one reason — a document uploaded through the browser is converted to text and stored there, so that an uploaded document and a copied-in one are the same thing by the time anything indexes them. Gemini is the only external service: one model answers, another embeds, and with semantic chunking the embedding side is called at index time for every sentence as well as for every finished chunk.

The third caller matters structurally. An MCP client — Claude Code, an IDE agent — reaches the same two tools the chat interface uses, over POST /mcp, without going near the browser application. It is not an integration bolted on afterwards; it is the same code path.

LEVEL TWO · INSIDE THE SYSTEM

Five containers, one published port

The exposure is the design. Only ui publishes anything, and it publishes to loopback; Postgres and Qdrant are reachable on the compose network and nowhere else.

The gateway being one process rather than two is the main structural decision. An MCP server and a chat gateway that calls MCP tools need exactly the same things — the corpus, the vector store, the embedding model, the auth check — so splitting them would mean running two jars to duplicate one set of connections, and adding an HTTP hop between a chat turn and its own retrieval.

The two stores split by responsibility rather than by convenience. Postgres holds the only copy of the text; Qdrant holds vectors and ids. Because chunk.id is also the Qdrant point id, one integer names a passage in both, and the vector index can be dropped and rebuilt from Postgres alone.

Document conversion is in the gateway rather than beside it. Apache Tika is a library, not a service, so an uploaded PDF becomes text in the request thread that received it — no queue, no worker container, no state that can be half-written. It is most of the weight of the image and none of its moving parts, which is the trade this system keeps making.

LEVEL THREE · INSIDE THE CONTAINERS

One definition, two callers

The gateway's fifteen Kotlin files arrange into two paths that meet at a shared foundation: answering a question, and indexing a document. Both reach the same four components, and ask them opposite things.

Tools.kt holds the two tools and the MCP JSON-RPC dispatcher over them. The chat agent calls Tools.call in-process, with no HTTP hop; an MCP client reaches the identical function through Http.kt. There is no second implementation to drift, so the model answering in the web interface and the model in someone's editor see the same tool descriptions and get the same results.

The indexing side gained two components and kept its shape. Extract.kt is Tika behind one method — bytes and a file name in, text and a media type out — so every caller downstream of it sees a string and does not know or care whether a PDF was involved. Semantic.kt is the chunker: it embeds sentences, bunches them by cosine similarity against the running centroid, and stamps each document with the settings it used. Chunker.kt, the paragraph rule, is still there as the fallback for an embedding API that is not answering — which is why the stamp records which of the two ran.

THE BROWSER SIDE

The single-page application holds something the server deliberately does not: the conversation. Postgres stores chunks, per the brief — which has the side effect that a question is never written to a disk the person asking it does not own. The cost is that a thread does not follow you to another machine, and signing out clears it.

4

LEVEL FOUR · WHAT ACTUALLY HAPPENS

Three paths through the parts

A question being answered, a file being indexed, and the one piece of configuration that silently rejects every token when it is wrong.

PATH ONE · A CHAT TURN

One request, held open for as long as the model takes. Everything is surfaced as it happens, so the interface can show what was retrieved even when the model cites none of it.

PATH TWO · A FILE BEING INDEXED

No queue and no watcher. A file lands in the folder — copied in by hand, or written there by POST /upload — and the same path below indexes it. The difference is only when: an upload runs it inside the request, while a file copied in waits for the next tick, one minute at most. That cadence is affordable because an unchanged corpus costs a read and a hash and nothing else.

PATH THREE · THE TWO KEYCLOAK URLS

The issuer and the JWKS URL point at the same realm and are deliberately different strings. Getting this wrong rejects every token, with a message that sends you looking somewhere else entirely.

THE SHAPE OF WHAT IS ABSENT

Named, so each is a decision

Every box that is not in the diagrams above was left out on purpose. These are the ones worth knowing about.

No reranker
A cross-encoder rerank would measurably improve ordering, and it needs a local model — the one dependency this build exists to avoid. Reciprocal rank fusion over the two retrievers is the ranking.
No document permissions
Everyone who can sign in can search everything. The corpus is one folder, and per-document permissions need a source of truth for them that a folder is not.
No server-side transcripts
Conversations live in the browser's localStorage. A question is never written to a disk the person asking it does not own; the cost is that a thread does not follow you to another machine.
No delete from the UI
Documents go in through the UI; they come out by deleting the file. The folder stays the source of truth, and one direction of write is a much smaller thing to reason about than two.
No OCR
Tika reads a document's text layer; a scanned page has none, and reading it needs Tesseract installed beside the gateway. An upload with no text in it is refused with that as the reason rather than indexed empty. On the scan path nothing is converted at all: a file that fails the extension test or a strict UTF-8 decode is logged and skipped, because converting it would mean the gateway writing files into the folder that nobody asked it to write.
Term hashing rather than a dictionary
BM25 terms hash to 31-bit indices, so nothing has to keep a term table in sync between indexing and querying. Two terms can collide; at 2³¹ slots against a vocabulary in the tens of thousands that is a ranking nuisance, not a correctness problem.
